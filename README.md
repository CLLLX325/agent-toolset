# 多工具 Agent 任务助手

一个不依赖 LangChain / LangGraph 的 ReAct Agent：模型自己决定调用哪个工具、传什么参数，
拿回结果再继续，直到能回答用户问题。全部代码约 600 行，每一步都能打印出来看。

## 它解决什么问题

客服问题往往不是"查一句话"能答的，比如：

> 「A2016 的咖啡机 699 元，按 30% 补偿应该赔多少？」

要回答它，得先查订单（确认金额和状态），再查补偿政策（确认 30% 这个比例），最后做乘法。
单纯把问题丢给模型，它只会编一个数字；单纯上 RAG，它又不知道去查订单表。

Agent 的做法是：给模型四个工具，让它自己规划调用顺序：

| 工具 | 作用 |
|---|---|
| `query_orders` | 对订单 SQLite 表执行只读 SQL |
| `search_policy` | 在政策语料里做 BM25 检索（复用 P1 的 24 篇语料） |
| `calculate` | 四则运算（AST 白名单，禁函数调用） |
| `date_diff` | 两个日期的天数差 |

## 目录结构

```
02-agent-toolset/
├── agent.py        # 主循环：思考 → 动作 → 观测，最多 8 步
├── tools.py        # 四个工具 + 注册表 + 统一的错误返回
├── db.py           # CSV → SQLite，只读查询白名单
├── prompts.py      # 四版 system prompt（v1~v4），用于对照实验
├── tasks.jsonl     # 30 条任务：问题 + 标准工具序列 + 答案关键词
├── run_eval.py     # 确定性判分，输出指标
├── test_agent.py   # 9 个单元测试（不调模型）
├── data/orders.csv # 30 条订单
├── results-*.json  # 每一轮评测的原始结果
├── 讲解.md          # 逐节讲解：架构、踩坑、面试问答
└── README.md
```

## 快速开始

```bash
# 前提：本机 Ollama 已启动，且有 qwen2.5:7b
python -m pytest test_agent.py -q          # 单元测试，秒级
python agent.py "A2012 这个订单买了什么，多少钱？"   # 单条交互
python run_eval.py --variant v3 --tag v3   # 全量评测（30 条，约 2 分钟）
```

## 实验结果

固定 30 条任务、固定模型（qwen2.5:7b）、温度 0，**每个版本跑 3 次**，三次结果完全一致
（单次结果有约 3% 的波动，见下方"已知局限"）。

| 提示词版本 | 关键改动 | 成功率 | 工具覆盖 | 工具序列精确 | 平均步数 |
|---|---|---|---|---|---|
| v1 | 只给工具清单 | 50.0% | 86.7% | 76.7% | 2.37 |
| v2 | 加字段说明 + 算术/日期分工 + 步数上限 | 83.3% | 90.0% | 90.0% | 2.07 |
| **v3** | v2 + few-shot 示例 + 一步一工具 | **90.0%** | **93.3%** | **93.3%** | 2.10 |
| v4 | v3 + 列名对照 + 空结果自查 | 90.0% | 93.3% | 93.3% | 2.13 |

- 成功率定义：答案含全部关键数字 **且** 工具序列是标准序列的子序列。
- v1 失败的典型原因：模型凭空编列名（`order_status`、`order_amount`），
  查不到就直接回答"订单表里没有这个字段"——这是 50% → 83% 的主要收益来源。
- v4 **没有带来提升**，反而让提示词长了约 200 token，因此不采用，保留 v3。

### 还剩哪 3 条失败

| 任务 | 现象 | 归因 |
|---|---|---|
| t02 / t25 | 把 `order_date`（下单日）当签收日 | 模型混淆两个日期字段 |
| t27 | 只查订单就作答，没查政策 | 抄近路：算出来的答案"看起来对"就收工 |
| t29 | 心算出正确数字，但没调 `calculate` | 违反任务约定（必须用工具） |

这三类都不是"运气不好"，而是真实生产环境会遇到的：字段语义歧义、模型偷懒、
规则遵从度不足。

## 关键设计

1. **强 JSON 协议 + 解析容错**：Ollama `format:"json"` 约束解码，代码再兜底取最外层花括号。
   30 条 × 12 次运行，解析失败数为 0。
2. **错误回灌**：解析失败、工具报错都作为一条 user 消息塞回对话，让模型自己改，
   而不是抛异常终止任务。
3. **工具沙箱**：SQL 必须 SELECT 开头、禁分号、禁写操作、强制 LIMIT 50；
   计算器用 AST 白名单只放行数字和四则运算。
4. **确定性判分**：不用 LLM 当裁判，改用关键词 + 工具子序列两条硬规则，可复现、可解释。

## 已知局限

- 评测集同时也是调提示词的依据（属于开发集），真实泛化效果会更低。
- 温度 0 下仍有约 3% 的单次波动：同样的问题，一次答对、一次把城市名写进 `customer` 列。
  所以结论都按"跑 3 次"给出。
- 只测了 qwen2.5:7b。换更小的模型（0.5B）会明显变差，换 GPT-4 级别会明显变好，
  这组数字只代表"本地小模型 + 普通提示词"的水平。
